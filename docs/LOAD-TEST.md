# 부하 테스트 (2026-11-21)

전시장 관람객이 몰릴 때 운영 서버가 버티는지 확인했다. 스크립트는 [`deploy/loadtest/`](../deploy/loadtest).

## 방법

- 도구: k6. 맥(한국)에서 운영 서버(시드니 EC2 t3.small)로 직접 요청
- 시간: 2026-11-21 00:34~00:47 KST (사용자가 없는 시간)
- 관람객 한 명의 흐름 (`visitor.js`)
  1. 게스트 생성 → 닉네임 `k6t_…` (정리용 표시)
  2. 홈 피드 → "삼성" 검색 → 기존 토론 열기(SSE 재생 + 차트)
  3. 타임머신 퀴즈 5문제 (문제마다 2~5초 읽는 시간)
  4. 오늘 랭킹
- 전시장 노트북 화면 1대: 15초마다 랭킹·피드 갱신
- 부하: 30초 동안 PEAK의 1/3 → 1분 동안 PEAK → 2분 유지 → 20초 감소
- **새 토론은 시작하지 않았다.** LLM 호출이라 비용이 들고, 워커 동시 2개 제한에 먼저 걸려 서버 측정이 안 된다
- 끝난 뒤 `run.sh cleanup`으로 테스트 게스트 771명과 퀴즈 답 3,855개를 지웠다

## 해석과 한계

- 전시장 동시 접속(수십 명)에는 여유가 있다. 병목은 서버가 아니라 LLM 호출이고, 이는 워커 동시 2개·1인 하루 5회·하루 비용 상한으로 막는다.
- **콜드 스타트**: 데우지 않은 첫 요청은 6초(스모크 테스트), 30명 테스트 첫 30초에는 워커 CPU가 162%까지 올랐다. 전시 당일 아침에 사이트를 한 번 돌려 둔다.
- **6~7초 지연 (100명)**: 여러 API의 최대값이 같은 순간에 6~7초였다. 특정 API가 아니라 서버 전체가 잠깐 멈춘 것으로 보이며, 원인은 확인하지 못했다(JVM GC 가능성).
- 실패 2건(30명·100명 각 1건)이 어느 API인지는 기록하지 못했다.
- 운영 서버라 100명에서 멈췄다. 한계점(어디서 무너지는지)은 측정하지 않았다.
- 새 토론 생성, 판정 제출, 카카오 로그인은 포함하지 않았다.
