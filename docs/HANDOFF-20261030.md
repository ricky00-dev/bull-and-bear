## 시작할 브랜치

저장소는 `https://github.com/ricky00-dev/bull-and-bear`이며, **`chore/worker-handoff-20261030`**에 최신 develop의 안정화와 이번 작업을 모았다. 이 브랜치를 받으면 기능별 커밋을 다시 cherry-pick할 필요가 없다. 원격 develop에는 이미 안정화 PR #17이 `447cdf4`로 병합되어 있었고, 이번 이관 작업은 develop에 직접 푸시하거나 PR을 병합하지 않는다.

```powershell
git clone https://github.com/ricky00-dev/bull-and-bear.git
cd bull-and-bear
git fetch origin
git switch --track origin/chore/worker-handoff-20261030
git status --short
git log -10 --oneline
```

이미 clone한 폴더라면 `git status`로 기존 변경을 먼저 확인하고 `git fetch origin`부터 진행한다. 로컬에 같은 브랜치가 있으면 `git switch chore/worker-handoff-20261030`을 사용한다. 파일을 강제로 덮어쓰는 reset·clean은 필요하지 않다.

개발 규칙은 [AGENTS.md](../AGENTS.md), 작업 이력은 [WORKLOG.md](WORKLOG.md), 설계는 [worker-rag-design.md](worker-rag-design.md)에 있다. 세션 시작 시 `bash scripts/session-brief.sh`를 실행한다. Windows에서는 Git Bash를 사용할 수 있다.

**`BULLBEAR_RAG_ENABLED=false`를 유지한다.** 환경 변수만 켜면 실제 Retriever import에서 실패한다. 주입 fixture가 통과했다는 것이 실제 검색 구현이나 운영 활성화 완료를 뜻하지 않는다. 기존 7거래일 코스피 초과수익 판정과 3거래일 보조 채점, 같은 종목·종가 날짜 토론 재사용, Spring 판정 봉인 계약은 유지한다.

`bullbear rag sync`도 현재는 로컬 JSON capture를 적재한다. 외부 뉴스·공시를 자동으로 조회하는 수집 스케줄러나 기사 본문 크롤러는 아직 없다. 지식 설명만으로 RSI·MACD·ROIC·FCF 같은 미구현 종목 지표를 생성하지 않는다.

## 환경과 검증

Python 3.12 이상·uv, JDK 17 이상, Docker 엔진을 준비한다. 기존 컴퓨터의 `.venv`·절대 경로·Docker 상태는 다른 컴퓨터로 옮겨지지 않는다.

```powershell
cd ai-worker
uv sync --locked --group dev
$env:PYTHONPATH = (Join-Path (Get-Location) 'src')
$env:BULLBEAR_RAG_ENABLED = 'false'
uv run pytest -q -p no:cacheprovider
```

Bash에서는 `PYTHONPATH="$PWD/src" BULLBEAR_RAG_ENABLED=false uv run pytest -q -p no:cacheprovider`로 같은 확인을 할 수 있다. 여러 작업 공간의 editable 설치가 섞이지 않도록 실제 import 위치를 확인한다.

Java는 `java -version`이 17 이상인지 확인하고 API 폴더에서 `./gradlew.bat test`를 실행한다. Linux/macOS는 `./gradlew test`를 사용한다. 전체 Java 회귀는 Testcontainers를 사용하므로 Docker 엔진이 필요하다. 별도 개발 DB를 띄울 때만 루트 `docker compose up -d`를 실행하며 기본 포트는 5433이다.

## 키와 로컬 자료

API 키·`.env`·원문 데이터·DB·캐시·가상환경은 푸시하지 않는다. 다른 컴퓨터에서 별도로 안전하게 설정해야 한다. 키 값을 작업 로그나 채팅에 붙이지 않는다.

이전 컴퓨터에는 OpenAI와 데이터 공급자 키가 있으나 Anthropic 키는 없었다. 현재 운영 HTTP LiveRunner는 Anthropic이며 OpenAI는 내부 benchmark/experiment 경로다. 실제 운영 검증은 Anthropic 키를 설정하거나 별도 provider 선택 기능을 먼저 구현해야 한다. 어떤 경로든 실제 역할별 모델·호출/비용 상한을 명시하고 시작한다.

필요한 설정 이름은 `ANTHROPIC_API_KEY`, `OPENAI_API_KEY`, `KRX_API_KEY`, `OPENDART_API_KEY`, `NAVER_CLIENT_ID`, `NAVER_CLIENT_SECRET`, Spring과 워커에 같은 `WORKER_TOKEN`이다. 선택한 공급자의 키만 해당 실행에 필요하다. 실제 값은 이 문서에 없다.

## 다음 작업

이관 브랜치에서 상태를 확인한 뒤 `git switch -c feat/worker-rag-retrieval`로 다음 기능을 분리한다. 이 브랜치는 선행 기능을 포함한 이관 체크포인트에 의존한다. develop을 대신 갱신하거나 기존 기능 커밋을 다시 적용하지 않는다.

1. `rag/retrieval.py`의 `Retriever(store).retrieve(snapshot, generation_id=...)`를 구현한다. 기존 `rag/store.py`, `context.py`, `index.py`의 실제 인터페이스를 먼저 읽는다.
2. common 최대 2문단·short 최대 3문단, 각 후보 20, 시장/종목/시점/검수 필터, 중복 제거, 온전한 문단 예산, 1초 deadline, empty/failed/timeout 구분을 구현한다. 현재 context는 합계 5문단만 제한하며 2/3 경로별 한도는 미구현이다.
3. 세대 공개/파일 손상/동시성/최신 활성 원문·주석·미래 세대 검사와 실제 검색 감사·불변 저장/load_context·debate 연결을 완성한다. 현재 index.open은 manifest 해시만 검사하므로 FTS/member 내용 정합성 검사가 남아 있다.
4. 정답 문단 집합을 가진 검색 평가와 실제 저장→검색→HTTP/benchmark 연결을 검증한다. 기존 HTTP 검사는 주입 Retriever 기반이다. 공개 Fact/[E#]/새 근거와 K 배경 인용을 섞지 않는다.
5. 같은 스냅샷·모델·정책에서 RAG 없음/공통+단기 추가를 비교한다. 실제 모델 tokenizer·가격표·입력 여유·추가 배경 비용 검증은 남아 있다. 실제 기간이 끝나기 전 예측 성능 향상을 주장하지 않는다.
6. 각 작업 후 평가 문서와 WORKLOG를 갱신하고 기능별 커밋한다. P1의 품질/완료율/지연/비용 기준과 11/16 프리즈를 고려해 위험 검토·LangGraph는 다음 우선순위로 유지한다.

초기에는 기존 전향 운용과 최소 RAG를 우선하고, 중장기 실제 판정·벡터·자동 가중치 변경·실행 재개를 동시에 늘리지 않는다. 외부 계약이나 공개 knowledge_refs가 필요하면 worker-api.md의 공동 검토 절차를 따른다.
