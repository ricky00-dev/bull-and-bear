# 아키텍처 결정 기록

설계를 정할 때마다 **결정 · 대안 · 이유**를 남긴다. 발표 때 "왜 이렇게 만들었나"의 근거가 된다.
전체 구성도는 `README.md`, Spring ↔ 워커 계약은 `docs/worker-api.md`.

2026-11-02 현재 구현 구조는 [워커 README](../ai-worker/README.md#기능-아키텍처),
실모델·통합 검증 결과는 [최신 인계](evaluations/worker-goal-readiness-20261102.md)를 참고한다.
아래 병렬화·캐싱은 설계 제안이며 아직 적용하지 않았다.

## 핵심 문제: LLM 토론은 느리다

토론 한 번 = 발언 6번(매수·매도 × 3라운드) + 검증 반려 시 재시도 + 중재자 1번.
재시도와 도구 조회를 포함하면 수 분이 걸릴 수 있다. 11/02 v8 실측은 토론 292.570초 후 실패했으며,
완주 시간은 아직 측정하지 못했다. 사용자가 진행 상황을 볼 수 있도록 확정 발언을 차례로 전달한다.

그래서 지연을 네 층에서 줄인다. 위에 있을수록 효과가 크다.

| 층 | 방법 | 효과 | 상태 |
|---|---|---|---|
| 1. **안 기다리게** | 같은 데이터면 재사용 + 장 마감 뒤 미리 돌려 두기 | 완료 결과 재사용 시 새 생성 대기 없음 | 재사용·스케줄러 구현, 운용 활성화는 별도 |
| 2. **덜 기다리게** | 서로 독립인 발언을 병렬로 | 고정 3단계로 실행, 실제 지연은 별도 측정 | LangGraph 구현 |
| 3. **진행 상황을 보이게** | 확정 발언부터 스트리밍, 재연결 시 이어 받기 | 검증 완료 발언부터 전달, 지연 보장 없음 | ✅ 구현 |
| 4. **호출 자체를 빠르게** | 전 역할 Sonnet, 스냅샷 프롬프트 캐싱 검토 | 품질·비용 절충 | Sonnet 적용, 캐싱은 실험 단계 |

### 1. 안 기다리게: 데이터 기준일로 재사용 + 사전 계산 (ADR-1)

**결정**: 토론 재사용 키를 `(종목, 데이터 기준일)`로 한다. 데이터 기준일 = 워커가 알려 주는 최신 종가 날짜.
DB 유니크 인덱스 `(ticker, data_date) where status <> 'FAILED'`로 강제한다.

**이유**: 토론 결과를 정하는 건 입력 데이터(스냅샷)다. 10/22 16:40에 만든 토론과 10/23 오전 10시에 만들 토론은
둘 다 10/22 종가 데이터를 쓴다. 그러니 다시 돌릴 이유가 없다. 처음에는 "같은 날(KST)"을 키로 썼는데,
그러면 자정에 캐시가 비고 다음 날 오전 사용자가 다시 1~2분을 기다린다.

**결과**:
- 전향 운용 스케줄러가 장 마감 뒤(16:40) 고정 종목을 미리 돌려 두면, 그 종목은 **다음 날 장 마감 전까지 누구도 기다리지 않는다**.
- 인기 종목은 첫 사용자 한 명만 기다리고 나머지는 재사용한다. 비용도 같은 비율로 준다.
- 동시 요청은 유니크 위반을 잡아 먼저 들어간 토론을 재사용한다 (분산 락 없이 DB 하나로 해결).

**대안**: 사용자가 종목 화면을 열면 미리 토론 시작(추측 실행) → 안 누르는 사람이 많아 비용 낭비, 기각.
인기 종목을 장 시작 전에 미리 돌리기 → 검색 로그가 쌓이면 검토 (전시 직전 상위 종목 사전 계산).

**주의**: 워커 `GET /stocks/{ticker}`의 `as_of`는 "지금 토론을 만들면 스냅샷이 쓸 날짜"와 같아야 한다 (계약 v0.4).

### 2. 덜 기다리게: 발언 병렬화 (ADR-2, LangGraph 적용)

현재 HTTP·CLI 워커는 LangGraph로 같은 라운드의 양측을 병렬 실행한다. 양측이 끝난 뒤 다음 라운드로 진행하며, 각 발언은 공개 전 검토를 기본 적용한다:

```
개회:   매수 개회 ─┐  매도 개회 ─┐      ← 서로 안 봐도 됨 → 병렬
반박:   매수 반박(매도 개회를 반박) ┐ 매도 반박(매수 개회를 반박) ┐  ← 병렬
마무리: 매수 마무리 ┐ 매도 마무리 ┐                              ← 병렬
중재자
```

병렬화하면 발언 호출 단계를 6단계에서 3단계로 줄일 수 있다. 실제 시간 감소는 양측 지연·재시도·도구 호출에 따라 달라지므로 측정이 필요하다.

같은 라운드의 상대 발언을 먼저 보는 정보 차이는 줄일 수 있다. 다만 선공·후공에 따른 실제 유불리와
다른 순서 편향까지 사라지는지는 별도 실험이 필요하다. 검토 재시도와 비용 예약 한도로 실제 지연이 늘어날 수 있다.

- 이벤트 계약은 그대로 쓸 수 있다 (`turn_started`/`statement_accepted`가 두 측에서 섞여 올 뿐). Spring·웹은 이미 `side`로 구분한다.
- 웹은 같은 라운드 두 발언을 순서대로 보여 주면 된다 (도착 순서와 무관하게 매수 → 매도).
- **담당: jangwonii**. `LiveRunner → GraphRuntime → build_debate_graph`가 고정 6발언과 최종 중재를 실행한다.

### 3. 기다림을 체감 못 하게: 확정 발언 스트리밍 + 재생 가능한 이벤트 로그 (ADR-3)

**결정**: 워커 → Spring → 브라우저를 SSE로 잇고, Spring은 모든 이벤트를 `debate_events`에 `seq`와 함께 쌓은 뒤 중계한다.

- 브라우저는 스냅샷 준비 후 첫 이벤트(`snapshot_created`)를 받고, 발언은 검증을 통과하는 대로 하나씩 받는다.
  최초 데이터 수집이 필요하면 더 오래 걸리므로 1초 응답을 보장하지 않는다.
- 끊겼다 다시 붙으면 `Last-Event-ID`부터 이어 받는다. 이미 끝난 토론은 DB에서 처음부터 재생한다.
  → 재사용 토론도 "진행되는 토론"처럼 볼 수 있다 (층 1과 결합).
- 워커 연결이 끊기면 Spring이 마지막 `seq`부터 재구독한다 (지수 백오프 5회). 서버가 재시작돼도 진행 중 토론을 이어 받는다.

**토큰 단위 스트리밍은 하지 않는다.** 검증기가 발언 전체를 보고 근거 수치를 대조한 뒤에야 확정되기 때문이다.
검증 전 토큰을 흘리면 반려될 발언이 화면에 나갔다가 사라진다. 대신 확정 발언에 클라이언트 타이핑 효과를 준다.

**대안**: 폴링 → 지연·부하 모두 나쁨. WebSocket → 서버 → 클라이언트 단방향이라 SSE로 충분하고, 재연결·Last-Event-ID가 표준에 있다.
메시지 큐(Kafka 등) → 규모에 비해 과함. 이벤트 로그 테이블이 큐 + 재생 저장소 역할을 같이 한다.

### 4. 호출 자체를 빠르게 (워커)

- 현재 기본은 토론자·중재자·단일 분석 모두 Sonnet 5.5이며(11/9 변경) 자동 모델 대체는 사용하지 않는다.
- 스냅샷을 공유하므로 프롬프트 캐싱을 검토할 수 있지만 현재 적용하지 않았다.
  선택적 HTTP 비용 장부도 캐시 쓰기를 허용하지 않으므로 도입 시 가격·예약 정책을 함께 검증해야 한다.

## 부하·비용 보호 (ADR-4)

| 장치 | 위치 | 이유 |
|---|---|---|
| 사용자당 하루 새 토론 5회 | Spring | 한 명이 크레딧을 다 쓰는 것 방지 |
| 사용자 토론 하루 $3, 전향 운용 하루 $4 | Spring | 월 $200 안에서 끝내기. 사용량은 워커가 `usage`로 보고 |
| 전향 운용 동시 2개 | Spring | Anthropic 속도 제한·워커 부하 |
| 재사용 우선 | Spring | 상한에 걸려도 기존 토론은 항상 볼 수 있다 |

Spring의 하루 예산은 추정 입장 제한이며 실제 공급자 지출의 강제 상한과 다르다.
워커에는 별도로 SQLite 트랜잭션 기반 최대 비용 예약·정산 장부를 구현했다. 선택 설정이며 실제 운영에는
아직 활성화하지 않았다. 범위와 미확정 처리·재시작 정책은 [운영 안내](WORKER-OPERATIONS.md)를 따른다.

**전시 당일(동시 접속 수십 명)**: 관람객 대부분은 재사용 토론과 타임머신 퀴즈(저장된 토론 재생, LLM 호출 없음)를 쓰므로
새 LLM 호출 수는 재사용 비율에 따라 달라진다. 워커는 `WORKER_MAX_CONCURRENT`(기본 2)로
동시 작업을 제한하며, 상한을 넘는 새 작업은 거부한다. 대기열은 현재 구현이 아니다.

## 기타 결정

- **판정 봉인은 Spring 책임**: 워커는 판정을 그대로 보내고, Spring이 저장만 하고 브라우저에는 `debate_sealed`로 가린다.
  사용자가 판정을 낸 뒤에만 `/reveal`로 연다. 워커가 실수해도 새지 않게 한 곳에서 막는다.
- **Spring ↔ Python 분리 (ADR-5)**: 서버를 나눈다고 토론이 빨라지지는 않는다 (시간 대부분은 Anthropic API 응답 대기,
  서버 사이 홉은 수 ms 늘어남). 나눈 이유는 속도가 아니라 **응답성·확장·장애 격리**다.
  - 응답성: 수 분 걸리는 LLM 작업과 Spring의 검색·판정 요청 처리를 분리한다.
  - 확장: 역할별 확장 경계를 유지한다. 다만 현재 워커는 데이터 폴더당 프로세스 하나만 허용하므로 복제만으로 확장할 수 없다.
  - 장애 격리: 완료된 토론·판정은 Spring에서 조회한다. 새 시세가 필요한 채점은 워커 복구 후 재시도한다.
    Spring은 마지막 seq부터 이어 받지만, 워커 재시작 당시 진행 중이던 생성은 실패로 정리하며 자동 재개하지 않는다.
  - 언어 강점: KRX/OpenDART 데이터 처리·Anthropic SDK는 Python, 인증·트랜잭션·스케줄링은 Spring.
  - 경계는 HTTP + SSE 계약 하나로 좁혔다. Spring은 가짜 워커로 워커 없이 개발·테스트한다.
- **거래일 달력을 두지 않는다**: 채점은 기준일 뒤 실제 시세가 있는 날을 세어 N번째 종가를 쓴다. 휴장일 관리가 필요 없다.
- **시계 주입**: "오늘"은 모두 주입된 `Clock`(KST)으로 계산한다. 테스트와 QA에서 날짜를 옮겨 채점·재사용을 검증한다.
